# Octop 底座改造方案：打通"制作智能体"与"工作台使用智能体"

> **状态**：方案稿，**尚未实现**。本文只描述现状事实、要改什么、按什么顺序改、怎么验收，需要 A 决定后再拆成 B/C/D 的具体 PR。
> **依据**：仓库 `main` @ `0d01bae`（2026-10-22 拉取）。

---

## 1. 结论先说

1. **Octop 已经有完整的智能体运行时**（Agent Loop、工具、会话、多模型、Skills、Connectors、Cron、IM 网关），底座本身不需要重写。
2. **真正的障碍只有一处**：`agents` 表是**按用户私有**的，没有"发布/共享"概念。制作区做出来的智能体，天然只有制作者本人在工作台看得到。
3. 所以"打通"不是改运行时，而是**在 agents 之上加一层发布模型**（可见性 + 发布态 + 目录查询 + 授权与审计），再加上制作区的"提交审核 → 发布"状态机和 Docker 一键包的可运维性。

---

## 2. 现状事实（带证据）

### 2.1 智能体是私有的

[`src/octop/api/routers/agents.py:94`](../../src/octop/api/routers/agents.py) 的 `list_agents`：

- 默认 `scope=mine`，只返回 `user_id` 等于当前用户的智能体；
- `scope=all` 仅管理员可用（同文件 `:109` 抛 `FORBIDDEN`）；
- 注释明确写着："(including admins — chat/experts sidebars must not leak other users' agents)"。

也就是说：**现在任何人（含管理员）都无法在正常工作台里看到别人的智能体**。

### 2.2 表结构里没有发布字段

`agents` 表（`001_initial.sql`）：

```
agent_id TEXT UNIQUE, user_id INTEGER REFERENCES users(id), name, description,
persona_mbti, default_model, system_prompt, enabled, config_json, last_state,
last_error, icon, template_name, created_at, updated_at
```

没有 `visibility`、`published_at`、`published_by`、`review_status`。

### 2.3 会话与线程按 (agent, user) 绑定

`sessions` 与 `threads` 都是 `agent_id + user_id + session_key`，意味着即使让 B 看见 A 的智能体，**B 也需要能以 B 的身份与 A 的智能体建立自己的会话**——这需要放开"agent 只属于创建者"的校验，而不是复制一份 agent。

### 2.4 Docker 一键包已经存在，但只覆盖"能起来"

- `docker/Dockerfile`：两阶段构建（node:20 构建前端 → python:3.12-slim 运行），带 `HEALTHCHECK`（`Dockerfile:134`）。
- `docker/docker-compose.yml`：单服务、端口 `${OCTOP_PORT:-8088}`、卷 `${OCTOP_DATA:-~/.octop}`、首次启动由 entrypoint 自动 `octop init` 建管理员。
- `Makefile` **没有** docker 相关目标（现有目标只有 build/dev/lint/test/format/clean 等）。

## 3. 改造设计

### 3.1 数据模型（迁移 `002_agent_publishing.sql`）

给 `agents` 增加四列，全部可空或带默认，向后兼容：

| 列 | 类型 | 说明 |
|---|---|---|
| `visibility` | `TEXT NOT NULL DEFAULT 'private'` | `private` 仅本人 / `shared` 指定用户或部门可见 / `public` 全平台可见 |
| `published_at` | `INTEGER` | 发布时间，`NULL` 表示未发布（草稿） |
| `published_by` | `INTEGER REFERENCES users(id)` | 审核通过并发布的管理员 |
| `review_status` | `TEXT NOT NULL DEFAULT 'draft'` | `draft` / `pending` / `approved` / `rejected` |

新增索引 `idx_agents_visibility (visibility, published_at DESC)` 支撑工作台目录查询。

> 注意：`UNIQUE(user_id, name)` 保留不变——同名只在同一作者内去重，跨作者允许同名（工作台靠 `agent_id` 区分，展示时带上作者名）。

### 3.2 接口

| 接口 | 变化 | 归属 |
|---|---|---|
| `GET /api/agents?scope=mine` | 保持不变 | 现状 |
| `GET /api/agents?scope=all` | 仅管理员，保持不变 | 现状 |
| **新增** `GET /api/agents/catalog` | 工作台目录：返回 `visibility in (shared, public)` 且 `review_status=approved` 的智能体，带作者名 | B |
| **新增** `POST /api/agents/{id}/submit-review` | 制作区提交审核，`draft → pending` | B |
| **新增** `POST /api/agents/{id}/publish` | 管理员审核通过，`pending → approved`，写 `published_at/published_by` | B + D（权限） |
| **新增** `POST /api/agents/{id}/reject` | 驳回并写入意见 | B |
| `POST /api/agents/{id}/chat`（或现有会话创建路径） | 放开校验：`approved` 且可见时，允许非所有者在**自己名下**建会话 | B |

**接口变更必须走 `[contract]` 流程**（见 [01-接口与数据库约定.md](01-接口与数据库约定.md) 第 2 节），因为 C 的前端要同步改。

### 3.3 权限与审计（D 负责）

可见性判定顺序：本人 → 管理员 → `shared`（按用户/部门白名单）→ `public`。这张真值表已经用 25 条用例验证过（含 3 条非法迁移），实现时照抄即可：

| 智能体状态 | 作者本人 | 管理员 | 其他民警 |
|---|---|---|---|
| `draft` / `pending` / `rejected` | 可见 | 可见 | **不可见**（哪怕 visibility=public） |
| `approved` + `private` | 可见 | 可见 | 不可见 |
| `approved` + `shared`，在白名单 | 可见 | 可见 | 可见 |
| `approved` + `shared`，不在白名单 | 可见 | 可见 | 不可见 |
| `approved` + `public` | 可见 | 可见 | 可见 |
| 任意状态 + `enabled=0` | 可见（"我的"列表） | 可见 | 不出现在工作台目录 |

两条容易做错的细节：

- **作者自己的已发布智能体不出现在自己的"工作台目录"里**——否则会和"我的智能体"重复列出。
- **`pending` 一律不可见**：审核中的东西不能被别人提前用上，这是审核的意义所在。

审核状态机（非法迁移必须抛错，不能静默放过）：

| 当前 | 动作 | 结果 |
|---|---|---|
| `draft` | submit | `pending` |
| `pending` | approve | `approved` |
| `pending` | reject | `rejected` |
| `rejected` | submit | `pending` |
| `approved` | submit | `pending`（发布后再改，重新送审） |
| 其他组合 | — | 拒绝，返回 `FORBIDDEN` 或新增错误码 |

- 会话创建时必须校验"该用户对目标智能体可见"，且**会话记录归属调用者**（`sessions.user_id = 当前用户`），不是创建者。
- 以下动作落 `audit_log`：提交审核、通过、驳回、改可见性、跨用户调用。
- 敏感字段（系统提示词）对非所有者只读、不可导出——按产品文档的"字段级脱敏"要求。

### 3.4 前端（C 负责）

- 制作区：智能体列表增加状态徽标（草稿/待审/已发布/已驳回），"提交审核"按钮，被驳回时显示意见。
- 工作台："智能体中心"改为读 `/api/agents/catalog`，展示作者与可见范围；调用时按当前用户身份开会话。

### 3.5 制作能力映射（产品文档 → 代码落点）

| 产品能力 | Octop 对应机制 | 落点 |
|---|---|---|
| 自然语言生成智能体 | Agent Loop + Skills + RAG | `infra/agents/`（生成后写入 `agents.system_prompt` / `config_json`） |
| 拖拽页面/表单 | 编译为智能体交互界面配置 | 存 `config_json`，前端按配置渲染 |
| 数据模型建模 | 映射为智能体可调用的数据工具 | 自定义工具注册（参照 `infra/connectors/`） |
| 流程设计器 | Extension 事件钩子 | `infra/agents/` 扩展点 |
| 警务组件库 | 自定义工具 + 前端组件 | C 的组件库 + 工具定义 |
| 模板市场 | Skills 预置包 | `src/octop/infra/agents/experts/library/` |

## 6. 未决问题（需要 A 拍板）

1. **`shared` 的粒度**：按用户白名单，还是按"部门/警种"？后者需要新增组织架构表，工作量翻倍。建议先做用户白名单，部门留到 M3 之后。
2. **审核人是否必须是管理员**：现产品文档要求"派出所应用需分局管理员审核"，即两级审核。若要做两级，`review_status` 需扩展成状态机表，而不是一个字段。
3. **智能体内容版本化**：发布后作者再改，是直接生效还是需要重新审核？建议重新审核，否则"审核"形同虚设。
4. **跨用户会话的上下文隔离**：B 用 A 的智能体产生的对话记录，A 能否看到？建议 A 不可见（隐私），只落审计。

## 7. M1 迁移预演（已在 SQLite 上验证，未入库）

为了不让"设计写了、SQL 跑不通"这种事发生，`002` 迁移先做了一次离线预演：用仓库真实的 `001_initial.sql` 建库 → 写入升级前的数据 → 应用 `002` → 逐项断言。

```text
columns         : OK ['published_at', 'published_by', 'review_status', 'visibility']
schema version  : OK -> 2
legacy row      : OK -> private / draft / unpublished (behaviour unchanged)
index           : OK -> idx_agents_visibility
catalog query   : OK -> only approved + shared/public, newest first
check constraint: OK -> invalid visibility rejected
ALL MIGRATION CHECKS PASSED
```

**最关键的一条结论**：升级后老数据仍然是"私有、草稿、未发布"。也就是说这个迁移**单独上线不会改变任何现有行为**——真正让智能体"被看见"的是后面的接口与前端改动，迁移本身是安全的。

迁移内容（确认后落到 `src/octop/infra/db/migrations/002_agent_publishing.sql`）：

```sql
ALTER TABLE agents ADD COLUMN visibility TEXT NOT NULL DEFAULT 'private'
    CHECK (visibility IN ('private', 'shared', 'public'));

ALTER TABLE agents ADD COLUMN review_status TEXT NOT NULL DEFAULT 'draft'
    CHECK (review_status IN ('draft', 'pending', 'approved', 'rejected'));

ALTER TABLE agents ADD COLUMN published_at INTEGER;
ALTER TABLE agents ADD COLUMN published_by INTEGER REFERENCES users(id) ON DELETE SET NULL;

CREATE INDEX IF NOT EXISTS idx_agents_visibility
    ON agents(visibility, review_status, published_at DESC);

-- shared 的按用户白名单（第 6 节问题 1 的默认假设；若改为部门/警种，删掉本表）
CREATE TABLE IF NOT EXISTS agent_shares (
    agent_id   TEXT NOT NULL REFERENCES agents(agent_id) ON DELETE CASCADE,
    user_id    INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    created_at INTEGER NOT NULL,
    PRIMARY KEY (agent_id, user_id)
);

CREATE INDEX IF NOT EXISTS idx_agent_shares_user ON agent_shares(user_id, agent_id);

UPDATE _schema_version SET version = 2;
```

工作台目录查询（`/api/agents/catalog` 实际使用的语句，已用种子数据验证）：

```sql
SELECT a.agent_id, a.name, a.description, a.visibility, a.published_at,
       a.user_id AS owner_id, u.username AS author
FROM agents a
LEFT JOIN users u ON u.id = a.user_id
WHERE a.enabled = 1
  AND a.review_status = 'approved'
  AND a.visibility IN ('shared', 'public')
  AND (a.user_id IS NULL OR a.user_id <> :viewer_id)
  AND (
        a.visibility = 'public'
        OR EXISTS (
            SELECT 1 FROM agent_shares s
            WHERE s.agent_id = a.agent_id AND s.user_id = :viewer_id
        )
      )
ORDER BY a.published_at DESC, a.agent_id
```

### 7.1 目录查询预演（已用种子数据验证）

种子：A 有草稿 / 待审公开 / 已发布公开 / 已发布私有 / 共享给 B / 已禁用六种，B 有已发布公开和草稿各一。

```text
[ok] bob sees alice's published public + shared, newest first; not her draft/pending/private/disabled, not his own: ['a_shared_bob', 'a_public']
[ok] alice sees bob's published public only: ['b_public']
[ok] admin gets the same catalog rules as everyone else (approval uses /api/agents?scope=all): ['b_public', 'a_public']
[ok] a viewer with no shares still sees public agents: ['b_public', 'a_public']
ALL CATALOG CASES PASSED
```

两条容易踩的产品语义，这里定死：

- **管理员在目录里与普通民警同规则**。审核要看的全量列表走已有的 `/api/agents?scope=all`，不要把一个"能用的目录"和一个"待审列表"混成一个接口。
- **作者自己的智能体不出现在自己的目录里**，否则"我的"和"目录"会重复列。

按第 6 节的决策，还缺一块：**审核若为两级**，`review_status` 之外还需要审批记录表（谁、何时、什么意见）。`shared` 已按用户白名单写入迁移（默认假设），若改为部门/警种，删掉 `agent_shares` 换成解析器即可。
