# 协作与 PR 审核流程

> **适用对象**：A（审核与合并）、B/C/D（提交方）、E（回归测试）。
> **原则**：`main` 谁都不能直接推，包括管理员。所有改动走 PR，审核通过才合并。

---

## 1. 分支模型

`main` 已由 Ruleset `protect-main` 保护，实际生效的规则（2026-10 核对）：

| 规则 | 现状 | 含义 |
|---|---|---|
| 禁止删除分支 | 生效 | `main` 删不掉 |
| 禁止强制推送 | 生效 | 改不了已有历史 |
| 必须走 PR | 生效 | 直接 `git push origin main` 会被拒 |
| 需要审批 | 1 人 | 提议人不能自己批自己 |
| 推送后旧审批失效 | 生效（`dismiss_stale_reviews_on_push`） | 批过之后再推新提交，要重新批 |
| 未归属提交额外审批 | 生效（`require_extra_approval_for_unattributed_changes`） | 见下方"提交邮箱" |
| 管理员豁免 | **无** | 管理员也一样走 PR |

> **提交邮箱**：最后一条规则要求提交能归属到 GitHub 账号。请确认 `git config user.email` 是你 GitHub 账号验证过的邮箱，否则你的 PR 会被要求额外审批。

### 分支命名

| 角色 | 分支示例 |
|---|---|
| B 制作区 | `feat/authoring-nl-generate`、`fix/template-market-filter` |
| C 前端 | `feat/workbench-three-column`、`feat/police-components` |
| D 数据库权限 | `feat/db-audit-log`、`feat/data-isolation` |
| E 测试文档 | `docs/runbook`、`test/smoke-suite` |

一人一分支，一个 PR 只做一件事。分支要短命，超过两周没合就拆分或关闭。

## 2. 提交方标准动作

```bash
git checkout main
git pull                                   # 开工前必须拉最新，否则基于旧代码写的会冲突
git checkout -b feat/你的功能名
# …改代码…
git add .
git commit -m "feat(workbench): 三栏布局骨架"
git push origin feat/你的功能名
```

然后在 GitHub 网页发起 PR，**指定 A 为 reviewer**，并在 PR 描述里写：

1. 这个 PR 做了什么（一两句）；
2. 怎么验证（跑了什么命令、看到什么结果）；
3. 有没有接口/表结构变更（有就填 `[contract]` 模板，见 `01-接口与数据库约定.md` 第 2 节）。

---

## 3. A 的审核清单

审核不是看代码像不像，是**拉下来跑一遍**。顺序如下：

### 3.1 静态检查（先过一遍，5 分钟）

- [ ] PR 只改了该改的文件，没有夹带无关格式化/重命名
- [ ] 没有直接改 `src/octop/dashboard/`（那是构建产物，源头在 `dashboard/`）
- [ ] 模块边界没破：`infra/` 没 import `api/`，router 里没写业务规则，没在 router 直接写 SQL
- [ ] 有新迁移：编号是 `002_*.sql` 而不是改 `001`，且 `_schema_version` 断言同步
- [ ] 有接口变更：带了 `[contract]` 前缀、更新了 `docs/api.md`、群里通知过
- [ ] 有错误码新增：`ErrorCode` + 后端 `i18n` + 前端 `apiErrors` 三处齐

### 3.2 跑一遍（关键步骤，见第 4 节脚本）

**自动化门禁（CI）**

仓库里已有 `.github/workflows/ci.yml`，每次 PR 会在 Ubuntu 与 Windows 上各跑一遍 `make install` → `make lint` → `make typecheck` → `make test`。这是"系统没崩"最可靠、也最省人力的来源。

> **现状提醒（2026-10-22 核对）**：本仓库是 `jubaoliang/Octop` 的 fork，而 **fork 默认不运行工作流**——Actions 页面里一条运行记录都没有（`total_count=0`，工作流列表为空）。必须由仓库管理员在 Actions 页面点一次 **"Enable workflows"**，CI 才会生效。在那之前，所有 PR 都没有自动测试。

**本地与手工检查（CI 未能覆盖时，或改动涉及界面交互时）**

- [ ] `make all` 绿（lint + typecheck + test）
- [ ] 动了前端：`cd dashboard && npx tsc --noEmit` 绿
- [ ] 动了 i18n：`uv run pytest tests/unit/i18n -q` 绿
- [ ] 动了 Docker/依赖：`docker compose -f docker/docker-compose.yml build` 成功，容器起来后 `/api/health` 返回 200
- [ ] 手动点一遍新增/修改的功能路径，确认系统不崩

### 3.3 结论

- **通过** → 用 Squash merge 合并（保持 `main` 线性、一个 PR 一个提交）。
- **驳回** → 在 GitHub 留意见，指明 `文件:行号` + 期望行为 + 怎么复现。不要只说"不行"。

合并后再做两件事：删掉远程功能分支；在群里同步"xx 已合并，E 可以拉最新回归"。

## 4. 审核脚本

`scripts/review-pr.ps1` 把"拉取 PR → 建独立工作目录 → 跑测试 → 报告"串起来，避免污染你正在写的分支。

```powershell
# 只看 diff 和改动文件，不跑测试
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/review-pr.ps1 -Pr 12 -SkipTests

# 完整审核：拉取 + make all + 前端 typecheck
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/review-pr.ps1 -Pr 12

# 额外做 Docker 冒烟
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/review-pr.ps1 -Pr 12 -Docker
```

脚本在 `.review/pr-<编号>/` 建独立工作树，退出码：`0` 全部通过、`1` 有检查失败、`2` 参数或环境问题。

## 5. 环境要求（每台开发机都要有）

| 工具 | 版本 | 说明 |
|---|---|---|
| uv | 最新 | 项目**只用** `uv run`，不要裸 `pytest` |
| Python | 3.12（由 uv 托管） | `pyproject.toml` 要求 `>=3.12`；不建议用 3.14，部分依赖没有预编译轮子 |
| Node | 20.x | 前端构建（Dockerfile 里也是 node:20-slim） |
| Docker Desktop | 最新 | 跑一键启动包；WSL2 后端 |

首次准备：

```powershell
# 安装 uv（Windows）
powershell -ExecutionPolicy ByPass -c "irm https://astral.sh/uv/install.ps1 | iex"

# 装 Python 3.12 与项目依赖（必须带 --frozen，理由见 5.1）
uv python install 3.12
uv sync --frozen

# 前端依赖
cd dashboard; npm ci
```

### 5.1 三个已经踩过的坑（2026-10-22 实测）

**坑 1：不锁版本会拉到一个跑不起来的依赖。**
`pyproject.toml` 里写的是 `orcakit-harness-agent>=0.9.10`，直接 `uv sync` 会解析到 **1.0.14**；1.x 移除了 `harness_agent.messages.first_user_text`，于是 `tests/unit/gateway/test_mention_agent_calls.py` 在**测试收集阶段**就 `ImportError`，整个套件一条都跑不了。锁文件里是 `0.9.10`，`harness-gateway` 是 `0.8.5`。

→ **一律 `uv sync --frozen`**，不要用 `uv pip install -U` 或 `pip install -e .` 自由升级。

**坑 2：`[all]` 额外依赖里有三个只有源码包的云 SDK。**
`orcakit-harness-agent[all]` 会带进 `oss2`、`esdk-obs-python`、`aliyun-python-sdk-core`，它们在 PyPI 上**只有 sdist、没有 wheel**，安装时要现场编译；网络受限或缺编译工具链就会失败，而且报错会指向"构建失败"，看起来像代码问题。

→ 只是跑测试时，可以只装基础依赖（去掉 `[all]`），再按锁文件版本钉住 `orcakit-harness-agent==0.9.10` 与 `harness-gateway==0.8.5`。

**坑 3：受限环境里 `pytest` 会大面积报权限错误，那不是代码缺陷。**
在带强制文件权限管控的环境（企业安全软件、沙箱会话、容器化 IDE）里，测试要在临时目录建文件、`chmod 0600`、递归删目录，这些操作会被拒。实测某受限会话：**576 passed / 37 failed / 678 errors**，678 个错误全部是 `WinError 5`（拒绝访问），37 个失败集中在附件与路径处理用例。

→ 这类环境下 **`make all` 的红色不能当作"代码坏了"的证据**，反过来它的绿色也不可信；必须在能自由读写临时目录的环境（普通终端、CI、容器）里跑。审核结论以那种环境的结果为准。

> **A 的机器当前状态**：`uv 0.13.5` 已装在 `D:\deep01\octop\.tools\uv.exe`（从 PyPI 取 wheel 解压，不需要管理员权限）；`.venv` 为 Python 3.14.7 + 基础依赖；**Docker 尚未安装**。全量验证要在普通终端里跑。

## 6. 严禁事项（踩了就会炸）

1. 在 `main` 上直接写代码、直接推。
2. 用 QQ/微信传压缩包合并代码（丢历史、丢冲突解决记录）。
3. 开工前不 `git pull`，拿旧代码丢给 CodeBuddy 生成。
4. 改了接口不群里通知（前端会按旧字段写一整版）。
5. 为了"让它能跑"去 `--force` 推、去改别人的迁移文件、去注释掉失败测试。
